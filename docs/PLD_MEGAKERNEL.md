# PLD on the cohere-megakernel: design + plan (no GPU run yet)
Status 2026-11-07: design and CPU-tested reference only (`harness/mk_block.py`, `tests/test_mk_block.py`, 10 CPU tests incl. test_pld). No GPU spend. Evidence classes as in RESULTS.md.

## Why
Megakernel plain decode is 3.25-3.34 ms/token (H1, H11) vs 3.9 ms for the Triton fast executor (H9). PLD on the fast executor gives 1.15x (natural, H15) to 1.5x (ctx 2K) over its own plain (H13/H14). H11 found the megakernel has no multi-token causal verify of ONE sequence and no KV rollback, so PLD could not be built on it.

## Expected value (INFERRED, arithmetic only)
Block/step cost ratio decides the gain. Fast executor (H13, MEASURED): T=4 1.52x, T=9 2.20x of a T=1 step. Megakernel, cost-shape emulation (H11, rows = BS, real-union): T=4 1.45x, T=8 1.95x. A real single-sequence block should be a little cheaper still in attention (no 8 KV copies). So per-round overhead is ~5-12% lower than the fast executor and the plain step is 15-17% faster: expect PLD tok/s on the megakernel of roughly 1.2-1.3x the fast-PLD tok/s on the same task mix, i.e. ~1.35-1.5x over fast plain on natural mix and up to ~2x at ctx 2K copy-heavy tasks, IF the kernel block cost lands on the emulated curve. This is a projection, not a measurement; the H11 curve is synthetic-weight, and any real block kernel may miss it (launch/barrier cost per extra row).

## What must be built (in the pinned engine, patch like src/mk_selfspec/mk_selfspec.patch)
1. **Block attention instruction** (the real work). Today each of BS rows is an independent sequence with its own KV slot and one new position. Needed: T rows sharing ONE sequence's KV: row j has position p+j, writes K/V at slot p+j (global) or (p+j) mod R (sliding), and attends keys <= p+j (> p+j-W sliding). Contract and mask are `mk_block.block_mask`; the order is "all T K/V writes first, then T attention rows" (needs an intra-instruction or inter-instruction barrier between write and read; the existing per-layer dependency counter can carry it). Per-row position vector replaces the scalar seq_len for RoPE and mask.
2. **KV rollback = free by construction.** Global layers: KV append-only, a host-held committed length; rollback is `length = p+a+1`, rejected slots are overwritten next round. Sliding layers: allocate the ring with R = W + Tmax - 1 slots (not W). `test_ring_without_slack_breaks` shows R=W corrupts accepted rows inside a block; `test_rollback_exact_global_and_ring` shows R=W+Tmax-1 gives results exactly equal to sequential decode for all W/p/T/accept counts tried. No snapshot/restore or copy kernel needed. Memory cost: (Tmax-1) extra slots per sliding layer, negligible.
3. **Logits for all T rows** (lm_head over T rows, argmax per row on device; return T int32 ids, not logits). lm_head is at the HBM floor (0.37 ms), extra rows ride the same weight stream. Device-side accept (`mk_block.accept`) can come later; first version does it on host.
4. **MoE for T rows**: expert tiles are already per-row routed in the BS>1 path; the H11 emulation measured this path (union reads). Reuse as is.
5. **Variant per T**: JIT variants are BS-specialised, so compile T in {1,2,4,8} (draft cap 7) and pad a block up to the next variant with masked rows (what H11 did; padded rows cost ~0.4-0.6 ms each, so prefer T in {1,2,3,4,5,6,7,8} if compile time allows). Policy (`pld.Policy` backoff) should pick T from the cost curve, not a fixed gamma.
6. **Host loop**: reuse `pld.spec_loop` + proposers unchanged (CPU draft). verify(tcur, drafts) = launch variant T=1+len(drafts), read T ids. Same loop shape as H13, so the identity/near-tie analysis (H13/H14) transfers; EXACT mode needs the batch-invariance argument redone for the megakernel (row-count-dependent reduction orders in its GEMMs), which is unverified.

## Staged plan and kill gates
- S0 (done, CPU): reference semantics + tests (this commit).
- S1 (CPU/local build only if explicitly safe; else Modal CPU image): add per-row position vector + shared-sequence KV addressing + block mask to the attention instruction; unit-check against `mk_block` on tiny random tensors on GPU (A100/H100 ~5 min, <$0.3).
- S2 (H100, ~$0.5): block correctness vs the fast executor's block (`harness/fast_north.py` `_forward_block`) teacher-forced on 16 greedy tokens, T=2..8; gate: argmax agreement except bf16 near-ties (margin <= 0.25) as in H13.
- S3 (H100, ~$1): block cost curve T=1..8 at ctx 2K/8K. Kill gate: T=4 cost > 1.7x or T=8 > 2.3x of T=1 => PLD gain over fast-PLD disappears, stop.
- S4 (H100, ~$1.5): end-to-end PLD with proposer sam2 on the H13/H15 task sets, interleaved with fast-plain and fast-PLD in the same launch (ratios only, H13 variance note). Total plan <= $3.5 of the $5 allowance.
Honest effort estimate: S1 is days of CUDA (instruction decode, barriers, JIT variants), not hours; it was out of reach in the $4 H11 budget and remains so for a single short session. That is why this commit stops at the contract and tests.

## S2 verdict on the 4-9.5 raw max-abs dlogit (diagnosis from saved data, 2026-11-08)
Data: results/mk_block_s2_vast.json(l), 105 accepted rows, T=2,3,4,5,8 (B=2,4,4,8,8). Saved data has ONLY per-T aggregates (no per-row logits, margins, ref ranks), so the per-row questions cannot be answered from it.
- MEASURED: 0/105 argmax mismatches, 0 mismatches with margin > 0.25. max_abs_dlogit by T (B): 2(2) 6.82, 3(4) 6.32, 4(4) 6.11, 5(8) 4.22, 8(8) 9.50.
- MEASURED: no padding dependence. Unpadded cells (T=2,4,8) have 6.8/6.1/9.5, padded cells (T=3,5) 6.3/4.2; the largest error is an UNPADDED full block (T=8,B=8). No monotone trend in T or B.
- NOT determinable: rollback/KV contamination (rows after rejected rows) and error vs top-1 margin or logit scale. Metric is the max over the whole ~152k vocab per row and over rows, i.e. an extreme-value statistic of any single slot, not error at the winning token; the logit scale is not saved.
- INFERRED (weak): errors this large (a bf16 ulp at |x| 16-32 is 0.125-0.25, so 4-9.5 is ~16-76 ulp) are not explained by ordinary single-rounding bf16 noise at the top logits, yet 105/105 argmax agree, which a large systematic error at the top-1 slot would rarely allow. Consistent with either (a) bf16 noise amplified through 40+ layers with different reduction order (block vs BS=1 GEMM/attention tiling) hitting a tail slot, or (b) a real but small-magnitude systematic difference not on the winner. Verdict: UNRESOLVED, leaning bf16 reduction-order noise (INFERRED, not MEASURED); not proven. Do not claim exactness (bit-identity) for the block path; argmax agreement on 105 rows is the only measured guarantee, and 105 rows is too few to bound the flip rate on near-ties.
- Added to modal/mk_block.py for the next GPU run (kind=s2row per accepted row): ref_margin, ref_top, ref_rms, err_max, err_argmax_tok, err_at_top, err_rms, rel_err_max, ref_tok_rank_in_block (0 = agrees), blk_margin, padded, prev_rejected, acc, round, row, pos. Decision rule: systematic if err_at_top / rel_err_max is large (>~0.05 of ref_top) or ref_tok_rank_in_block > 0 beyond near-ties (ref_margin <= 0.25), or error clusters on prev_rejected=True or row index; bf16 noise if err_at_top is within a few ulps and error is uniform across padded/prev_rejected/row.

## S3 block cost curve -> projected PLD tok/s (CPU projection, all INFERRED, 2026-11-08)
Code: `harness/mk_projection.py` (uses `mk_block.project`), `scripts/project_mk_pld.py`, `tests/test_mk_projection.py`; output `results/mk_block_projection.json` (every table below, per kind/category, caps 2..8, best-T histogram). Inputs: MEASURED S3 curve (`results/mk_block_s3_vast.json`, T=1..8 at ctx 2K/8K), MEASURED acceptance: H13 natural-cell traces replayed through `pld.spec_loop` (sam2, exact per-round (drafts, accepted)); H13 ctx2K/8K cells and the H15 99-prompt mix only have per-task aggregates saved (padded prompts and generations were not kept), so they use a fitted iid per-position-hit model (ctx cells bracket the unknown mean draft length: dbar=abar / dbar=12). Model check on the 21 natural tasks: aggregate model vs exact replay, median error 0.8-1.7% on the MK/fast ratio, max ~10%; on the mix it gives fast-PLD/fast-plain 1.12/1.11/1.16 vs measured H15 1.151 (underestimates the tail of long drafts slightly). NOT a measurement: no end-to-end megakernel PLD run exists, host CPU/launch cost per round is ignored (same for both sides), S2 left batch-invariance/exactness unproven.

**The answer depends on one number that was NOT measured on one box: megakernel T=1 vs fast T=1.** The S3 curve is steeper than the fast executor's (T=4 x1.68 vs 1.54-1.60, T=8 x2.38/2.24 vs ~2.07), so the megakernel only wins through its cheaper plain step. Fast-executor cost tables differ by host between launches (fp2 T=1 3.96 ms ~ H9/H11 era; fp3 3.32 ms, 19% faster host; exact executor 4.56 ms), so three scenarios: fp2 (MK plain 1.19x fast plain), fp3 (parity, 1.00x), exact executor (H14/H15, 1.39x, but MK exactness unproven).

Copy-heavy classes (canitedit, quality_qa, squad_qa, extract) gain least over fast PLD because they want T>4 and the S3 curve is steepest there; free-form classes gain most because they are plain-step bound. Best T per task is mostly small (mix: T=2 for 42 tasks, 3 for 28, 4 for 10, >=5 for 19), so a T<=4 cap gives up only 1-4% vs free T on the mix and natural (6-10% on ctx cells with dbar=12).

**Does a T<=4 cap alone beat fast PLD? Yes only if the megakernel plain step is >=~1.03-1.05x faster than the fast plain step on the same box** (needed plain advantage for T=4 to tie fast PLD: 1.03 mix / 1.03 natural, 1.05-1.20 on ctx cells; for best-T 1.01 mix). With the H9/H11-era numbers (3.3 vs 3.9 ms) it wins by ~15% on the mix; at plain parity (fp3 host) it loses 2-3% on mix/natural and 5-12% on ctx cells, and even best-T only ties (1.006 mix, 58/99 tasks). So the S3 gate failure (T=8 2.38x) matters little by itself; the steeper-than-fast curve is the real cost, and the plan's expected 1.2-1.3x over fast PLD survives only with the MK plain-step advantage intact. A same-box MK vs fast T=1 and T=2..8 measurement would settle it (not run).

Break-even acceptance (iid per-position hit prob a, draft always available = best case; JSON `breakeven_iid_ctx2K`): an MK block at T must commit cost(T)/cost(1) tokens to tie MK plain: T=2 1.25, T=3 1.47, T=4 1.68, T=8 2.38 tokens, i.e. a >= 0.25 / 0.35 / 0.42 / 0.59, or equivalently >= 0.25 / 0.47 / 0.68 / 1.38 accepted drafts per draft round (this per-draft-round form does not depend on how often a draft exists). To beat fast PLAIN: a >= 0.03/0.18/0.28/0.49 (T=2/3/4/8, fp2), 0.24/0.34/0.41/0.58 (fp3). MK best-T (<=8) vs fast PLD best-T (<=13) at equal a: ahead on a in [0.03, 0.85] (fp2; peak 1.20x at a=0.3, 0.91x at a=0.9), only on [0.24, 0.53] (fp3; peak 1.05x, 0.79x at a=0.9): at high acceptance the fast executor's flatter T=8..13 curve and longer drafts win, so the cap of 8 and the 2.38x T=8 cost hurt exactly the copy-heavy tails.
